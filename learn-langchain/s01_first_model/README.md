# 第1课 换模型就要重写代码？先做一层统一的模型调用入口
很多人第一次写大模型代码，都是照着官方文档抄 SDK 调用，跑通的那一刻还挺有成就感。
但你很快就会遇到一个很现实的问题：换一家模型厂商，代码几乎要重写一遍；想加个重试、配个超时，全要自己动手；最别扭的是，明明问的是一句话，返回的却是一坨看不懂的结构。
这节课我们就来彻底搞懂：为什么最简单的“一问一答”也会这么麻烦？以及怎么用一套标准化的入口，把所有厂商差异都隔离开，让模型调用这件事先顺顺当当地跑起来。

---
## 先搞懂：直接对接 SDK 到底卡在哪？
你家里接电器的时候肯定有体会：不同牌子、不同国家的设备，插头形状都不一样。有的两脚扁插，有的三脚圆插，进口设备还要单独买转换头。每次换一个电器，就得折腾一次插座。

直接调用各家大模型的 SDK，和这件事一模一样。你本来只想做一件最简单的事：说一句话，拿到回答。可光是“连上模型”这件事，就能绊住你半天：
- 换一家厂商，从云服务模型换到本地开源模型，几乎所有调用代码都要重写；
- 密钥管理、客户端初始化、超时配置、重试逻辑……这些和“问答”本身无关的琐事，全要自己操心；
- 最反直觉的是：模型返回给你的根本不是一段纯文本，而是一个结构复杂的对象。你直接打印它，屏幕上显示的不是答案，是一堆带着元数据的结构体。

我们可以算一笔账：
假设你要支持 3 家模型厂商，每家的初始化、调用、返回格式都不一样。光是做格式对齐，就要写好几倍的重复代码。后面再加工具调用、流式输出，工作量还会翻倍。

所以结论很直白：
> 只要模型会换，直接对接 SDK 就永远是临时方案。这是所有大模型应用都会遇到的第一个边界问题。

还不只是换模型麻烦。
哪怕你只用一家模型，返回对象里藏着各种字段，初学者很容易搞不清哪个才是答案，踩各种低级错误。
所以我们要做「统一调用入口」，不只是为了少写代码，更是为了定下一套稳定的接口约定，让后面所有功能都能在同一个基础上往上搭。

---
## 最容易想到的办法，为什么走不远？
很多人第一反应：这还不简单？我写个函数，里面用 if-else 判断不同厂商，分别调用各自的 SDK，最后统一返回字符串不就行了？

这个思路能解决眼前的问题，但它绝对不是长久之计。就像你给每个插头都单独缠一圈胶带改形状，凑合用可以，但隐患特别多：
第一，**维护成本会越来越高**。
每多支持一家模型，你就要往函数里加一段分支逻辑，时间长了这个函数会越来越臃肿，改一处就要牵动全身。出了问题排查起来，要在一堆分支里来回跳。

第二，**能力扩展会非常累**。
今天你只需要发文本，明天要支持工具调用，后天要支持流式输出，每加一个能力，你都要在所有厂商分支里各写一遍，重复劳动特别多。

第三，**返回格式永远对不齐**。
每家 SDK 的返回对象都不一样，token 统计、错误信息、附加字段各有各的写法，你要花大量精力做格式对齐，还很容易漏东西。

所以正确的思路非常朴素，和标准化插座的逻辑一模一样：
> 不是让业务代码去适配每一家模型，而是定下一套标准接口，让所有模型都来适配这套标准。

我们接下来要讲的两步方法，就是严格按照这个逻辑来的：先定下模型实例的获取标准，再用统一的方式发起调用、提取结果。越靠前，越基础、越稳定；越靠后，越贴近具体业务。

---
## 第一步：通过统一初始化函数，获取标准模型实例
你肯定遇到过：换个电器就要换插座，最省事的办法就是全屋都换成标准插座。不管什么设备，插上去就能用。

我们的第一步 `init_chat_model` 干的就是这件事。
它就是一个标准插座：你给它一个带厂商前缀的模型名（比如 `openai:gpt-4o-mini`），它就会自动帮你初始化好对应的客户端，返回一个行为完全一致的模型对象。不管底层是哪家厂商，拿到手的对象用法都一模一样。

我们写一个函数来封装它：
```python
def build_model():
    model_name = os.environ["LANGCHAIN_MODEL"]
    return init_chat_model(model_name)
```

逻辑非常简单：
- 从环境变量里读取配置好的模型名称；
- 交给 `init_chat_model`，直接拿到可用的模型实例。

这一步是整个课程最基础的约定：
**一次初始化，全链路通用；换模型只改配置，不改代码。**
所以它永远是我们写大模型应用的第一步。后面每一节课都会用这个方式来获取模型对象。

---
## 第二步：发起调用，从返回对象中提取答案
模型实例拿到了，接下来就是发起请求。
你可能以为，传入一句话，得到的就是纯文本答案。实际并非如此——模型返回的是一个结构化的 **AIMessage 对象**，答案文本只是其中的一个字段。
这是很多初学者撞的第一堵墙：直接打印返回结果，看到的不是回答，是一堆结构数据。答案就存储在这个对象的 `content` 字段里。

```python
def ask_once(query: str, model=None) -> str:
    if model is None:
        model = build_model()
    response = model.invoke(query)
    return message_text(response)
```

逻辑也很直白：
- 用统一的 `.invoke()` 方法发送问题，不管底层是哪家模型，调用方式都一样；
- 拿到返回的 `AIMessage` 对象，用 `message_text()` 把里面的文本内容提取出来。

我们故意保留了显式提取的步骤，没有直接返回字符串，就是为了让你看清：模型的返回值本身是一个结构化对象，文本内容只是它的组成部分之一。这个返回对象中还包含 token 消耗统计、工具调用指令等很多扩展信息，后续课程会逐步用到。

> 这一节真正交付的，从来不是“成功调用了一次模型”，而是**那条清晰的边界**。你的代码只认 `invoke()` 和 `AIMessage`，不需要知道底层是哪家厂商。后面所有的课程——消息列表、提示模板、工具调用、Agent 循环——都会在这个基础上扩展，而“用统一接口拿模型实例”这条规矩，从第一课定下来就不会再变。

---
## 为什么这层封装必不可少？
讲到这里你应该已经能自己回答这个问题了。
不是我们非要多套一层函数，而是这层封装本身，就在你的业务代码和模型厂商之间，划了一条清晰的边界：
1.  **切换成本极低**：换模型只需要改环境变量里的字符串，业务代码一行都不用动
2.  **能力统一扩展**：后续加流式输出、加工具调用、加结构化输出，都只需要学一套 API
3.  **类型契约稳定**：输入输出的类型是固定的，你可以基于稳定的类型去构建上层逻辑

这就像家里的市电标准是 220V，所有电器都按这个标准做，电网那边不管是火电、水电还是风电，都不影响你家里电器的使用。`init_chat_model` 就是在做同样的事：把模型侧的差异，全部隔离在边界之外。

> 注意：`init_chat_model` 统一的只是调用接口，不会自动帮你安装所有厂商的依赖包。本仓库默认只安装了 `langchain-openai`；切换到其他厂商时，仍然需要安装对应的集成包并配置好密钥。
>
> 开头提到的重试、超时这类通用配置，也统一在这一层解决：`init_chat_model(model_name, max_retries=2, timeout=30)` 会把这些参数透传给底层客户端，不需要每家厂商各写一套。

## 动手试一试
现在你可以亲手跑一跑，看看第一次模型调用是怎么工作的。
先进入对应的文件夹运行程序：
```bash
cd learn-langchain
uv run python -m s01_first_model.code
uv run pytest s01_first_model/tests -q
```

### 实验1：观察返回值的真实类型
在 `ask_once` 函数里加一行打印：
```python
print(type(response))
```
运行后你会看到输出是 `<class 'langchain_core.messages.ai.AIMessage'>`。
这就是模型调用的真实返回形态：它不是纯字符串，而是一个结构化对象。真正的回答文本存储在 `response.content` 字段中，`message_text()` 只是帮你做了统一的文本提取。

### 实验2：不接 API 也能跑通测试
运行测试命令，你会发现即使没有配置真实的 API 密钥，测试也能全部通过。
因为测试用的是 `GenericFakeChatModel`，它是一个模拟模型，不会发起真实网络请求。这也是统一接口的好处：测试环境可以无缝替换成假模型，不影响上层业务逻辑。

### 实验3：查看返回对象的完整字段
在函数里打印一下 `response.usage_metadata`，你能看到本次调用的 token 消耗统计。
除了核心的文本内容和 token 消耗统计，返回对象中还包含 `tool_calls` 等扩展字段——这些现阶段暂时用不到，但你需要建立一个认知：模型返回对象承载的信息远不止一句文本回答。后续讲到工具调用和结构化输出时，我们还会反复用到这些字段。

## 本节课打下的地基
s01 是整个课程的地基，没有前置内容。本节确立的所有基础，后续课程只会扩展，不会改写：

| 基础约定 | 后续如何演化 |
| --- | --- |
| `init_chat_model` 统一入口 | 后续每节课都会用它来获取模型对象 |
| `model.invoke(query)` 调用方式 | 从 s02 开始会升级为显式消息列表调用，字符串输入仍然兼容 |
| `AIMessage` 统一返回对象 | s05 结构化输出会让返回值进一步升级为 Pydantic 对象 |
| `message_text()` 提取文本 | 全课程通用的文本提取工具 |

**本课引入的核心原语**：`init_chat_model` / `invoke` / `AIMessage`

> **本课程两条贯穿始终的主线**：
> 1.  所有对话上下文，都用消息对象来承载；
> 2.  所有组件都遵循统一的调用约定，明确声明自己的输入输出类型。
>
> 后面我们会陆续加入消息类型、提示模板、结构化输出、工具调用、Agent 循环、流式输出、记忆模块和检索增强。但无论加多少功能，模型的对话上下文始终由消息表达，单次调用始终用 `.invoke()`，流式场景改用 `.stream()`。你只需要记住这套统一的契约，就能顺着课程一步步搭出完整的系统。

## 本节课小结
这节课我们其实只讲了一个核心道理：
> 别直接对接具体厂商，先在边界上做一层统一的封装。把接口标准定下来，底层怎么变都不怕。

看起来只是多了一层函数调用，背后却是非常重要的设计思想——用稳定的接口隔离变化。有了这层统一入口，后面不管加多少功能、换多少模型，我们的核心代码都不用推倒重来。

但只发一句话很快就会不够用：模型每次调用都是“失忆”的，接不住上下文。下一节课，我们就来解决这个问题：怎么用一组消息，让模型记住对话的前因后果。
