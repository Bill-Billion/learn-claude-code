> *"An Agent without a plan makes it up as it goes"* — list the steps before acting so long tasks lose fewer pieces.
>
> **Harness layer**: Planning — maintain a task list through the `todo_write` tool.

---

By the end of the previous lesson, the Agent can work, be blocked, and be observed. Now give it a genuinely multi-step task: "Rename every Python file to snake_case, run the tests, and fix any failures."

It changes three files, runs the tests, finds two failures, and starts fixing them. Somewhere during that repair, the original renaming task disappears. The newest test failure has consumed all its attention.

The reason was already present in s01: the model has no memory, only context. The loudest thing in context is always the latest tool result, while the original goal sits dozens of messages away. Three steps into a ten-step refactor, the model starts improvising because steps four through ten have faded from attention.

## Why "Don't Forget the Goal" Is Not Enough

The first instinct is to emphasize the requirement in the system prompt: "Always remember the original task." But the goal is static and progress is not. Fixed text cannot remember that step 3 is complete while step 4 is halfway done.

Should the harness decompose the task and feed the model one step at a time? No. Decomposition is exactly what the model is good at. The harness does not understand the task well enough to break it down.

The right division of labor is: the model plans and records; the harness provides a place for that record and nudges the model when it stops maintaining it. That place is a new tool.

---

## todo_write: A Tool That Does No Work

`todo_write` cannot read files or run commands. It adds no execution capability. Its only purpose is to turn the plan in the model's head into a persistent, visible checklist with status:

```python
CURRENT_TODOS: list[dict] = []

def run_todo_write(todos: list) -> str:
    global CURRENT_TODOS
    todos, error = _normalize_todos(todos)   # Validate first; model-generated arguments are untrusted
    if error:
        return error
    CURRENT_TODOS = todos

    lines = ["\n## Current Tasks"]           # Render the live checklist in the terminal
    for t in CURRENT_TODOS:
        icon = {"pending": " ", "in_progress": "▸", "completed": "✓"}[t["status"]]
        lines.append(f"  [{icon}] {t['content']}")
    print("\n".join(lines))
    return f"Updated {len(CURRENT_TODOS)} tasks"
```

Pause at `_normalize_todos`. Tool arguments are generated by the model, and models make mistakes: they may wrap an array in a string or omit `status`. Validate first. If the input is wrong, return a clear error and let the model retry. This is the same philosophy as s02's `edit_file`: do not guess what the model meant; use an error to bring it back on track.

Integration reuses s02's motto: one definition, one registration, zero changes to dispatch.

```python
TOOLS = [
    ...,   # The existing five tools
    {"name": "todo_write",
     "description": "Create and manage a task list for your current coding session.",
     "input_schema": {"type": "object", "properties": {"todos": {"type": "array",
         "items": {"type": "object", "properties": {
             "content": {"type": "string"},
             "status": {"type": "string", "enum": ["pending", "in_progress", "completed"]}},
             "required": ["content", "status"]}}}, "required": ["todos"]}},
]
TOOL_HANDLERS["todo_write"] = run_todo_write
```

How does the model know when to use it? Add one instruction to the system prompt:

```python
SYSTEM = (
    f"You are a coding agent at {WORKDIR}. "
    "Before starting any multi-step task, use todo_write to plan your steps. "
    "Update status as you go."
)
```

The ideal rhythm is now: receive a task and create a checklist (all `pending`); mark the current step `in_progress`; mark it `completed` when finished; move to the next `pending` item.

But guidance is only guidance. Under pressure, the model may execute tools for several turns without touching the checklist. Once the checklist goes stale, it loses its value.

## Nag Reminder: Nudge It When It Forgets

The harness counts turns. If three consecutive tool-use turns pass without `todo_write`, it injects a reminder into `messages` before the next model call:

```python
rounds_since_todo = 0

def agent_loop(messages):
    global rounds_since_todo
    while True:
        # Inject a reminder after three turns without a todo update
        if rounds_since_todo >= 3 and messages:
            messages.append({"role": "user",
                             "content": "<reminder>Update your todos.</reminder>"})
            rounds_since_todo = 0

        response = client.messages.create(...)
        ...
            # Reset the counter when the model calls todo_write
            if block.name == "todo_write":
                rounds_since_todo = 0
```

Three details matter.

**The reminder uses the `user` role.** As s01 explained, `user` means information arriving from the outside world. Like a tool result, this reminder is the world's voice, not the model talking to itself.

**The reminder does not force anything.** The harness adds one sentence to context. On the next turn, the model still decides whether to update the list. Nudging it and doing the planning for it are fundamentally different designs; this code consistently chooses the former.

**The counter tracks turns, not calls.** One response may contain several tool calls. If none of them is `todo_write`, that response counts as one missed turn.

> Real Claude Code has no fixed "three turns" rule. Its nudge is smarter: if every checklist item is complete but none verifies the work, it reminds the model to add a verification step. It also has two task systems: an in-memory checklist like TodoWrite and a complete task system with file persistence, dependency graphs, and concurrency locks. We build the second one in s12.

## What's Next

The Agent can plan. But a task such as "refactor the entire authentication module" is still too large for one checklist: it contains dozens of subtasks, each reading many files and producing many intermediate results. Even a perfect checklist cannot stop one conversation from overflowing.

s06 Subagent → Split large work out. Give each subtask an independent Agent with clean context, then bring back only its conclusion.
