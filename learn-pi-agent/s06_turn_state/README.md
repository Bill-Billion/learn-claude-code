# s06 · Turn State

[← s05](../s05_tool_hooks/README.md) · [Contents](../README.md) · [s07 →](../s07_session_tree/README.md)

> In one sentence: before a turn starts, the harness snapshots the messages, tools, resources, model, and request options into one object — and that snapshot is all the turn ever reads, start to finish.
>
> Where this sits in Pi: `AgentHarness.createTurnState()` in the harness layer of `@earendil-works/pi-agent-core`.

→ `tools` and `activeTools` are two separate lists: register a whole pile, show the model only a handful this turn
→ systemPrompt can be a function — which tools and skills this turn has only comes together at snapshot time, so that's when it resolves
→ Swap the model or edit resources mid-turn and this turn doesn't care; the change isn't lost, it lands when the next turn takes a fresh snapshot
→ Before sending a request, real Pi runs one conversion step mini doesn't have: AgentMessage and LLM Message are not the same thing

---

## The problem

Picture a failure scenario. A turn is already in flight: the first provider call returned toolUse, the tool finished running, and the loop is about to send a second request carrying the toolResult. Right in that gap, something external touches the harness config — an extension swaps out the skills in resources, or the user switches models mid-run, or the headers in streamOptions get changed.

If every step of the loop read global state directly, the turn would contradict itself:

```text
the system prompt was built from the old skills, but the second request ships the new ones
the first half of the turn went to model A, the second half to model B
the two requests carry different timeouts and headers, and the logs can't explain what config this turn actually ran with
```

Bugs like this are hard to chase, because every individual step looks fine — what's wrong is that the world changed between two steps.

Pi's answer is to never let a turn touch global state directly: before the turn starts, snapshot every input into a turn state object, and read only the snapshot for the whole turn. External changes aren't lost — they just wait until the next turn takes a fresh snapshot.

## The idea

Write a `createMiniHarness()` with a single method, `createTurnState()`, which assembles a snapshot out of the session, the tool table, the resources, and the model config:

```text
messages       the current messages pulled from the session
sessionId      how provider caches and logs identify whose turn this is
systemPrompt   a fixed string, or generated by a function at snapshot time
model          which provider's model this turn uses
tools          every registered tool
activeTools    the tools the model actually sees this turn
resources      skills and prompt templates (what they really are can wait until s08)
streamOptions  request options like timeout, headers, metadata
```

Pi's snapshot carries one extra field, `thinkingLevel` (how hard to reason this turn); mini leaves it out.

This section only builds the snapshot — no provider calls yet.

## Run it first

```sh
npm run session:s06
```

The output looks like this:

```text
Session: demo-session
Messages: 1
Active tools: read
System prompt: tools=read skills=audit
Timeout: 30
```

The registry actually holds two tools, read and bash, but `activeToolNames` only lists read, so the model only sees read this turn. The `tools=read` in the system prompt is computed from that same list.

## How the code works

Three steps.

**Step 1**: the session exposes exactly two methods.

```ts
export function createDemoSession(id: string, initialMessages: MiniMessage[] = []): MiniSession {
  return {
    messages: initialMessages.map(cloneMessage),
    async buildContext() {
      return {
        messages: this.messages.map(cloneMessage),
      };
    },
    async getMetadata() {
      return { id };
    },
  };
}
```

`buildContext()` returns the messages this turn will use, `getMetadata()` returns the session id. Real Pi's session is a branchable entry tree (that's s07), but everything turn state asks of it is these two methods.

**Step 2**: the harness pins down the tool lists at creation time.

```ts
const tools = options.registry.tools.map((tool) => ({ ...tool }));
const activeToolNames = options.activeToolNames ? [...options.activeToolNames] : tools.map((tool) => tool.name);
validateActiveToolNames(tools, activeToolNames);
```

`tools` is everything registered; `activeToolNames` decides what's enabled this turn. An unregistered name or a duplicate in the list throws right here — not after a request has already gone out.

**Step 3**: `createTurnState()` takes the snapshot.

```ts
const context = await options.session.buildContext();
const metadata = await options.session.getMetadata();
const activeTools = activeToolNames.map((name) => tools.find((tool) => tool.name === name)!);
```

First pull the session context, then the session metadata, then select this turn's tools by name. Next comes resolving the system prompt — it can be a fixed string, or a function:

```ts
systemPrompt({ activeTools, resources }) {
  return `tools=${listActiveToolNames(activeTools)} skills=${resources.skills?.map((skill) => skill.name).join(",")}`;
}
```

A dynamic prompt isn't showing off: which tools and which skills this turn has only comes together at snapshot time, so that's the only moment it can resolve.

Last, the return value — every field gets its own copy:

```ts
return {
  messages: context.messages.map(cloneMessage),
  resources: turnResources,
  streamOptions: cloneStreamOptions(streamOptions),
  sessionId: metadata.id,
  systemPrompt: resolvedSystemPrompt,
  model: { ...options.model },
  tools: tools.map((tool) => ({ ...tool })),
  activeTools: activeTools.map((tool) => ({ ...tool })),
};
```

A snapshot has to act like one: once `createTurnState()` returns, mutating resources, streamOptions, or the session's messages must not affect a turn that's already underway. "Take a snapshot" instead of "read global state" is what gives every turn a stable starting point you can reason about. The s06 tests verify exactly this.

## The messages in the snapshot aren't the messages sent to the model

In mini, `turnState.messages` can go straight out the door, because a `MiniMessage` is already the shape an LLM understands: role plus content. Real Pi isn't like that.

Pi's internal AgentMessage carries far more than the model knows about: terminal-UI notices, custom messages injected by extensions, session entries, branch summaries... The model only understands standard LLM messages. So before each request actually leaves, Pi runs a conversion line mini doesn't have:

```text
AgentMessage[] -> transformContext() -> convertToLlm() -> Message[] -> LLM
```

You can see both steps in `streamAssistantResponse()` in `agent-loop.ts`: `transformContext()` first gets one chance to rewrite the context (AgentMessage[] in, AgentMessage[] out — housekeeping like compaction plugs in here), then `convertToLlm()` flattens the internal messages down to the standard Message[] a provider accepts.

This layer is what lets Pi keep arbitrarily rich state internally without polluting the request sent to the model — UI notices and extension-private data stay inside, and the model always sees clean standard messages. mini's message type is born LLM-shaped, so it skips the layer. But remember that real Pi has it: s09 runs into it again with extension custom messages — when an extension writes its own messages into the session, it's exactly this layer that decides whether the model sees them, and in what shape.

## Try it yourself

1. Change the demo's `activeToolNames: ["read"]` to `["read", "bash"]` and rerun — Active tools and System prompt change together, because both read the same list. Then change it to `["missing"]`, and `createMiniHarness()` throws `Unknown active tool: missing` on the spot.

2. Verify snapshot isolation. In `runDemo()`, take two snapshots back to back, vandalize the first, and see how the second holds up:

   ```ts
   const first = await harness.createTurnState();
   const second = await harness.createTurnState();
   first.activeTools[0].name = "hacked";
   console.log(second.activeTools[0].name);
   ```

   It still prints read. Now change `activeTools: activeTools.map((tool) => ({ ...tool }))` in the `createTurnState()` return value to plain `activeTools` and rerun — hacked bleeds into the second snapshot. That's the price of shared references, and it's exactly the shape Pi's shallow copy leaves behind, as covered in "Against the Pi source" below.

After changing things, run `npm run test:s06` to confirm you haven't broken this section's behavioral contract.

## Wiring into the main line

Before s06, a turn's inputs were scattered across the call site: provider, registry, and hooks were function arguments, with no session and nowhere to put the model or request config. s06 gathers "everything a turn needs" into one object:

| Component | Last section (s05) | This section (s06) |
| --- | --- | --- |
| A turn's inputs | loose arguments to `runHookedToolLoop(provider, registry, hooks)` | one snapshot from `createTurnState()` |
| Tools | whatever's in the registry, the loop can run | `tools` registers everything, `activeTools` picks per turn |
| Message source | the loop accumulates from an empty array | provided by `session.buildContext()` |
| system prompt / model / streamOptions | didn't exist | enter the snapshot as this turn's fixed config |

s06 is also the hub for the sections ahead: the resources in the snapshot get genuinely collected from the project in s08 (AGENTS.md, skills, prompt templates); streamOptions and sessionId are how different runtime shells sharing one core identify and configure requests in s10; and the session black box gets cracked open in the very next section.

## Against the Pi source

Read [pi-source.md](pi-source.md) after this section.

The mapping in one sentence: mini's `createTurnState()` corresponds to `AgentHarness.createTurnState()` at `agent-harness.ts:331-362` — the same `buildContext()` + `getMetadata()` + select tools by activeToolNames + resolve systemPrompt line, with Pi's snapshot adding one `thinkingLevel` field. One difference worth knowing: mini copies deeper than Pi — Pi's `getResources()` (`agent-harness.ts:981-986`) only `slice()`s the arrays, so the skill and template objects themselves are still shared references.
