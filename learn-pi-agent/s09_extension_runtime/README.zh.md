# 第9课 扩展运行时——内核不内置工作流，功能全靠扩展插进来

[English](README.md) · 中文 · [日本語](README.ja.md)

[← s08](../s08_context_resources/README.zh.md) · [目录](../README.zh.md) · [s10 →](../s10_runtime_modes/README.zh.md)

到s08为止，我们的内核已经很完整了：工具循环、会话树、上下文资源、钩子，该有的都有了。这时候很多人会想：别的Agent都有plan模式、子Agent、todo列表，我们是不是也应该内置这些功能？

先别急，Pi的官方README里明明白白写了三个No：
- **No sub-agents**：不内置子Agent
- **No plan mode**：不内置计划模式
- **No built-in to-dos**：不内置待办列表

很多人看到这三个No会觉得"这也没有那也没有，这框架也太弱了吧"。恰恰相反，这三个No是Pi最核心的设计哲学之一——不是做不了，是**不替所有人做决定**。

这节课我们就来讲扩展机制，看看这些功能怎么不写一行内核代码，全靠扩展实现。

---

## 先搞懂：为什么不把常用功能内置进内核？

你仔细想想就会发现，这些"常用功能"根本没有标准答案：
- 子Agent应该串行还是并行？上下文怎么隔离？结果怎么回传？
- 计划模式是写给人看还是写给模型看？计划要细到什么程度？
- Todo列表存在文件里还是跟着会话分支走？要不要自动勾选？

一百个团队有一百种用法，你把某一种写进内核，就等于强迫所有人用你的方式，不合适的人想改都改不了。而且功能一旦进了内核，就会有人依赖，以后想删都删不掉，内核会越来越臃肿。

正确的做法非常简单，就像手机系统：系统本身不内置所有App，它只提供一组标准接口——通知、相机、定位、分享。App安装的时候注册自己要用的接口，你装一百个App，系统本身一行代码都不用改。想用todo？装个todo扩展；想用子Agent？装个子Agent扩展；不喜欢别人写的？自己写一个，和系统自带的用起来一模一样。

Pi的扩展机制就是这个思路：内核只提供注册口和稳定的调用顺序，具体功能全靠扩展插进来。官方例子里的todo扩展、subagent扩展，全都是这么做的，一行内核代码都没改。

---

## 核心原则：注册不等于执行

扩展本质上就是一个js/ts文件，默认导出一个factory函数。加载扩展的时候，内核会调用这个factory，传给它一个pi对象，你在factory里做的所有事情，**都只是注册，不会立即执行**：

```ts
export default function(pi) {
  // 这里的代码只在加载扩展时执行一次，只做注册
  pi.registerTool({...}); // 注册工具
  pi.registerCommand({...}); // 注册斜杠命令
  pi.on("tool_call", () => {...}); // 注册事件监听
}
```

就像你装App的时候，App只是在桌面建了个图标、注册了自己要用的权限，不会一安装就自己跑起来。真正什么时候执行？等对应的事件发生的时候：
- 模型调用了你注册的工具，才会执行工具的handler
- 用户输入了你注册的斜杠命令，才会执行命令的handler
- 对应的事件触发了，才会调用你注册的事件监听

factory执行完，只是在内核那里登了个记，留了个联系方式，真正干活要等叫号。

---

## 扩展能做什么？

扩展能注册的东西主要有三类，覆盖了99%的需求：

### 1. 注册工具
用`pi.registerTool`注册新的工具，和内置工具完全一样——模型能看到、能调用，执行结果正常进上下文。
比如todo扩展就是注册一个todo工具，模型调用它来增删待办事项，和内置的read、bash工具没有任何区别。

### 2. 注册斜杠命令
用`pi.registerCommand`注册斜杠命令，用户输入`/命令名 参数`的时候触发。
比如/clear清屏、/help显示帮助、/model切换模型，都是这么实现的。

### 3. 注册事件监听
用`pi.on`监听内核事件，在合适的时机插入自己的逻辑，常用的事件有三个：
- `before_agent_start`：Agent开跑前触发，可以改system prompt、注入自定义消息
- `tool_call`：工具执行前触发，对应s05的beforeToolCall，可以拦截危险操作
- `resources_discover`：加载资源时触发，可以动态提供skill、prompt模板的路径

事件handler是按扩展加载顺序调用的，前一个handler改了system prompt，后一个handler看到的就是改后的版本，这个顺序是稳定的，不会乱。

---

## 几个重要的设计细节

### 扩展可以注入自定义消息
before_agent_start事件除了改system prompt，还可以往会话里注入自定义消息。
还记得s06我们提过吗？Pi内部的消息和给模型的消息是分层的，自定义消息就是内部消息：它可以带自定义类型、任意数据，`display`字段决定给不给用户看，转成给模型的消息时可以选择要不要给模型看。
比如计划扩展可以在这里把当前计划注入进去，统计扩展可以在这里塞个只给UI看的统计信息，非常灵活。

### 工具拦截是链式的
tool_call事件是按顺序问所有扩展的，只要有一个扩展返回`{block: true, reason: xxx}`，这个工具就被拦截了，不会执行，拦截原因会包成错误的toolResult给模型，和s05的钩子行为完全一致。
这就是为什么Pi不需要内置权限弹窗——你想要什么样的权限规则，自己写扩展拦就行：想拦所有rm命令？拦；想写文件前弹确认？拦；想只允许在特定目录操作？拦。怎么拦、拦什么，全是你自己的事，内核不替你做决定。

### 动态发现资源
resources_discover事件让扩展可以动态提供skill和prompt模板的路径，不需要用户手动配置。比如你装了个代码评审扩展，它自己就会把评审的skill路径报给内核，内核加载资源的时候自动就把这个skill加上了，用户完全感知不到。

### 所有能力都接在已有机制上
注意：扩展没有发明任何新机制，全是接在我们前面几节课写好的东西上：
- 注册的工具合并到s02的工具注册表里
- 动态发现的资源路径拼到s08的资源加载列表里
- tool_call事件接在s05的工具钩子上
- before_agent_start改的system prompt最终进s06的快照里

内核还是那个内核，只是每一环都留了个插座，扩展想插哪里插哪里。就像你电脑的USB口，插U盘、插鼠标、插键盘，电脑本身不用改，插上就能用。

## 动手试一试

### 实验1：自己写个todo扩展
在扩展列表里加一个最简单的todo扩展：
```ts
{
  path: "todo.ts",
  factory(pi) {
    const todos = [];
    pi.registerTool({
      name: "todo",
      label: "todo",
      description: "添加待办事项，列出所有待办",
      parameters: {
        type: "object",
        properties: { text: { type: "string" } },
        required: ["text"],
      },
      handler(input) {
        todos.push(String(input.text));
        return { content: todos.map((t, i) => `${i+1}. ${t}`).join("\n") };
      }
    });
  }
}
```
重跑你会看到工具列表里多了todo——你没改一行内核代码，就加了个新功能，就像装了个App。

### 实验2：写个拦截note工具的规则
再加个tool_call监听，如果调用的是note工具就拦截，返回{block: true, reason: "笔记已冻结"}。
重跑你会发现调用note工具会被拦截，拦截原因正常返回。把危险命令改成ls，就会正常放行。

跑完两个实验，你应该能回答下面检查点的问题。改完可以用`npm run test:s09`确认没破坏行为约定。

## 本节课打下的地基

s09我们实现了扩展机制，内核从此可以无限扩展而不用修改本身：

| 这节课立的约定 | 后面会怎么用 |
|----------------|--------------|
| 扩展加载时只注册，不立即执行，事件触发才调用 | 装扩展没有副作用，不会一加载就跑逻辑 |
| 扩展可以注册工具、命令、事件监听，能力和内置完全一致 | 第三方功能和内置功能体验一致，没有二等公民 |
| 事件按加载顺序链式调用，前一个的修改后一个可见 | 扩展之间可以协作，顺序稳定可预测 |
| 所有扩展能力都接在已有机制上，不新增内核逻辑 | 内核保持薄薄一层，不会因为加扩展变复杂 |
| 不内置workflow，具体实现交给扩展 | 不同团队可以用不同的工作流，互不干扰 |

**本课引入的核心原语**：`ExtensionAPI` / `MiniExtensionRunner` / `registerTool` / `registerCommand` / `on`

## 本节课小结

这节课我们其实只讲了一个核心道理：
> 内核只提供机制，不提供策略。什么功能好用、什么工作流适合你，你自己用扩展决定，内核不替你做选择。

看起来只是加了个注册机制，实际上这是Pi能保持内核小巧、同时生态无限扩展的关键——核心永远稳定，功能可以随便加。现在内核和扩展都有了，但我们现在只能在代码里调用函数，真实使用的时候，我们需要在终端交互、在CI里输出JSON、被别的程序当服务调用、嵌入到别的程序里，难道要写四套Agent？下节课我们就来讲运行模式，同一套内核接不同的外壳，满足所有场景。
