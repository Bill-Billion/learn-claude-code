# 第11课 信任与执行环境——90%的人都理解错了Pi的安全模型

[English](README.md) · 中文 · [日本語](README.ja.md)

[← s10](../s10_runtime_modes/README.zh.md) · [目录](../README.zh.md) · [s12 →](../s12_pi_package/README.zh.md)

现在你clone了一个网上找的陌生项目，里面有.pi目录、有扩展、有自定义配置，启动Pi的时候弹个框问你"是否信任此项目"，很多人想当然地以为：
- 点"信任"就全开，所有功能都能用
- 点"不信任"就锁死，不能读文件不能跑命令，安全了

如果你这么理解，就大错特错了。这是Pi最容易被误解的设计，也是90%的安全问题的来源。这节课我们就把这两个边界彻底讲清楚。

---

## 先搞懂：为什么"信任=安全开关"的理解是错的？

我们先做个实验，你就懂了：你clone一个陌生项目，启动Pi，点"不信任"，然后让它读你家目录下的.ssh/id_rsa，你猜它读得到吗？
答案是：读得到，不仅读得到，还能写文件、能跑shell命令，什么都能干。

很多人第一反应是"这不是bug吗？不信任怎么还能读我私钥？"
不是bug，这是故意这么设计的。因为Pi的"项目信任"和"执行安全"是两个完全独立、互不干涉的边界，谁也代替不了谁。

这个逻辑其实和生活里的小区门禁、银行金库是一模一样的：
- **小区门禁（Project Trust）**：管的是外来的人和东西要不要进小区——访客要登记，快递要检查，你同意了才让进。但门禁不是保险柜，人进了小区，你家里的东西他都能碰，门禁管不着你家里的事。
- **银行金库（Execution Environment）**：管的是贵重物品存在哪里、操作在哪里执行——真要安全，你得把钱存金库，把活放到隔离的环境里干，这是另一套完全独立的系统，和门禁没关系。

你不能说"我过了小区门禁，我家就不用锁门了"，也不能说"我不信任这个访客，他进了小区也碰不到我家东西"——这是两回事。

---

## 第一个边界：Project Trust 只是输入加载开关

Trust回答的问题非常非常窄：**这个项目里的.pi目录下的配置、扩展、prompt模板，要不要加载？**
它只回答yes或者no，除此之外什么都不管。

### 哪些东西需要过trust门？
只有会改变Pi行为的项目本地文件：
- .pi/settings.json 项目配置
- .pi/extensions/ 项目本地扩展
- .pi/prompts/ 项目本地prompt模板
- 父目录下的.agents/skills 项目本地skill

Trust通过了，这些东西就加载；没通过，这些东西就不加载。仅此而已。

### 哪些东西不过trust门？
非常重要：**AGENTS.md、CLAUDE.md这些说明文件，不管你信不信任，都会加载进上下文。**
为什么？因为这些是项目说明，Pi认为你打开一个项目，就应该看到项目的说明，哪怕你不信任这个项目。
但这也意味着：不信任的项目的AGENTS.md是会进模型上下文的，这就是一块天然的prompt injection面——恶意项目可以在AGENTS.md里写指令让模型干坏事，Pi明说这是本地Agent的预期风险，不承诺拦截这个。
你打开一个陌生项目的README，就相当于你看了陌生人写的东西，里面写什么你都可能看到，这是正常的，不要以为点了不信任就不会被AGENTS.md里的指令影响。

### Trust决策逻辑
Trust的决策顺序是固定的，非常简单：
1. 命令行传了--approve/--no-approve，直接用这个值
2. 项目里根本没有需要trust的输入（没有.pi目录也没有.agents/skills），直接信任
3. 信任扩展的决策，可以选择记住选择
4. 之前已经记住过这个项目的信任选择，直接用
5. 默认策略是always/never/ask
6. 如果是ask，而且是非交互模式（print/json/rpc），弹不了框，默认不信任
7. 如果是交互模式，弹框问用户，用户选什么就是什么

注意非交互模式默认不信任——因为没人能点确认框，安全起见默认不加载项目的扩展和配置。

## 第二个边界：Execution Environment 是工具执行的后端

Trust管的是"要不要加载项目自带的东西"，而工具执行的时候用什么权限、在哪里执行，是Execution Environment管的，和trust半毛钱关系都没有。

Pi默认的执行环境是本地环境：直接用你启动Pi的那个用户的权限，读本地文件、写本地文件、跑本地shell。也就是说，你用你自己的用户启动Pi，Pi就有你所有的权限——能读你的私钥、能删你的文件、能跑任何命令，不管你信不信任当前项目。
这不是bug，这是设计：Pi是本地编码助手，它本来就需要这些权限才能帮你改代码、跑命令。

执行环境是个可替换的插口，你可以换成不同的后端：
- 本地环境：默认，直接在本机执行，权限就是你的用户权限
- SSH环境：在远程机器上执行
- Docker环境：在Docker容器里执行
- 微VM环境：在轻量虚拟机里执行

隔离强度完全取决于你用什么后端：用本地环境就没隔离，用Docker就有容器级隔离，用VM就有虚拟机级隔离。

### 重点：进程内检查不是安全边界
很多人以为"我在代码里检查了路径不能出/目录、命令只能npm开头，就安全了"。
大错特错。这种进程内的前缀检查，一捅就破：
- 路径检查：`/repo/../root/.ssh/id_rsa` 就能绕出/repo目录
- 命令前缀检查：`npm test; rm -rf /` 是以npm开头的，直接放行，分号后面的命令照样跑

这种检查只是个"抽屉上的封条"，防君子不防小人，不是安全边界。**真隔离只有一个来源：操作系统/容器/虚拟机提供的边界**，也就是你把执行后端换成Docker或者VM，进程内的检查永远不算数。

Pi故意不做进程内沙箱，因为不完整的沙箱会给你虚假的安全感——你以为自己安全了，其实根本没有。真要隔离，就用真的隔离技术，不要自欺欺人。

## 先跑起来看看

```sh
npm run session:s11
```

输出长这样：
```text
Project trusted: false
Context files: /repo/AGENTS.md
Extensions loaded: 0
Local read still works: token
Contained bash: contained:/repo$ npm test
```

逐行看，你就懂了：
1. 因为是print非交互模式，所以trust默认是false
2. AGENTS.md照样加载了，进了context files——不信任也加载
3. 项目扩展一个都没加载——这是trust=false唯一做的事
4. 本地环境照样读了/repo/secret.txt的内容token——不信任也能读文件
5. contained环境只允许npm开头的命令，npm test正常执行

这几行就把所有误解都打破了：trust=false只是不加载扩展，别的什么都没拦。

## 动手试一试

### 实验1：把trust改成true
把模式改成interactive，加上promptDecision: true，再跑。
你会看到Project trusted变成true，Extensions loaded变成1——信任了就加载项目扩展，仅此而已，别的什么都没变，本地读文件还是能读。

### 实验2：绕过命令前缀检查
在contained环境里跑`npm test; rm -rf /tmp/x`，你会发现它放行了——因为是以npm开头的，分号后面的命令根本没被检查。
这就是为什么说进程内前缀检查不是安全边界，太容易绕了。

### 实验3：绕出目录限制
给contained环境加个路径前缀检查，只允许读/repo下的文件，然后试试读`/repo/../secret.txt`，看能不能读到。
你会发现只要没做路径规范化，../就能直接绕出去。

做完这三个实验，你就会明白：进程内的检查都是纸老虎，真安全得靠操作系统级别的隔离。

跑完三个实验，你应该能回答下面检查点的问题。改完可以用`npm run test:s11`确认没破坏行为约定。

## 本节课打下的地基

s11我们彻底讲清了Pi的安全模型，两个边界互不干涉：

| 这节课立的约定 | 后面会怎么用 |
|----------------|--------------|
| Project Trust只是.pi输入的加载开关，不是权限系统 | 不要以为点了不信任就安全了，该隔离还是要隔离 |
| AGENTS.md不过trust门，不信任也会加载 | 陌生项目的AGENTS.md天然是prompt injection面，要注意 |
| 非交互模式弹不了框，ask默认不信任 | CI/CD、脚本调用的时候记得显式加--approve如果需要加载项目扩展 |
| 执行环境是可替换插口，隔离强度取决于后端 | 要真隔离就换Docker/VM后端，不要信进程内检查 |
| 进程内的路径/命令前缀检查不是安全边界 | 不要把这种检查当沙箱用，防君子不防小人 |

**本课引入的核心原语**：`resolveProjectTrusted` / `loadProjectInputs` / `ExecutionEnv` / `createLocalExecutionEnv` / `createContainedExecutionEnv`

## 本节课小结

这节课我们其实只讲了一个核心道理：
> 信任是输入开关，不是安全锁。门禁代替不了金库，不要把"不加载项目扩展"当成"执行是安全的"。

这是Pi最反直觉但也最重要的安全设计，理解了这个你就不会犯那种"我点了不信任所以随便跑没问题"的低级错误。现在安全边界讲清楚了，最后一个问题：扩展、skill、prompt这些东西怎么打包分发？用户怎么安装别人写的扩展？下节课我们就讲包机制——包只是分发单元，不是新的运行时机制。
