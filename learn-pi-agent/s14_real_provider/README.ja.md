# s14 · Real Provider

[English](README.md) | [中文](README.zh.md) | 日本語

[← s13](../s13_integrated_harness/README.ja.md) | [目次](../README.ja.md)

> 一言で言うと、s14 は OpenAI 互換 Chat Completions の SSE を s03 の `ProviderEvent` プロトコルへ変換し、実モデルが統合済みの s13 ツールループを駆動できるようにします。
>
> Pi での位置づけは `pi-ai` のプロバイダー層です。正規化されたアシスタントイベントを `pi-agent-core` が受け取る直前にあります。

→ オフラインのフィクスチャは Harness の仕組みを決定的に再現できることを証明し、実プロバイダーはモデルが本当に次の行動を選べることを証明する
→ SSE チャンクは伝送上の断片であり、意味上のイベントではない。UTF-8 バイト、SSE レコード、JSON の差分、ツール引数は、四つの異なる境界で組み立てる
→ ツール引数は信頼できないモデル出力である。完全な文字列を JSON オブジェクトとして解析し、レジストリの検証を通過するまでは実行しない

---

## 問題

s01 から s13 は意図的に決定的なプロバイダーを使います。イベント順序、ツール実行、セッション保存、拡張機能のフック、信頼判定、パッケージ解決を学びやすく、安全にテストできるからです。しかし、重要な問いが一つ残ります。同じインターフェースは実モデルのストリームでも通用するでしょうか。

実際の Chat Completions 応答は、一つの `AssistantMessage` として届きません。任意に分割されたバイト列の中に SSE レコードが入っています。各 JSON レコードには、テキスト、ツール ID、関数名、関数の JSON 引数のいずれか一部分だけが含まれることがあります。リクエストは、レスポンスボディを受け取る前、読み取り中、または意味のある応答を途中まで受け取った後にも失敗します。

誤った近道は、ネットワークから届く各チャンクを `\n\n` で分割し、そのまま `JSON.parse()` することです。ネットワークチャンクの境界は、UTF-8 のコードポイントや SSE レコードの境界とは一致しません。SSE を解析した後でも、`tool_calls[].function.arguments` は呼び出しが完了するまで不完全な文字列です。

そこで s14 は、責務を絞ったアダプターを一つだけ追加します。以前に作ったループ、レジストリ、セッション、ランタイムの契約は変更しません。

## 考え方

送信経路では、既存の `ProviderContext` を変換します。

```text
systemPrompt             -> system message
user message             -> user message
assistant text/toolCall  -> assistant content/tool_calls
toolResult               -> tool_call_id を持つツールメッセージ
ToolDefinition           -> function tool schema
```

受信経路では、伝送層を順番にほどいていきます。

```text
ReadableStream<Uint8Array>
  -> streaming TextDecoder
  -> 完全な SSE レコード
  -> JSON Chat Completions チャンク
  -> テキスト / ツール呼び出しの蓄積器
  -> s03 ProviderEvent
  -> s05 ツールループ
  -> s13 セッション + ランタイム
```

アダプターは、対応している `finish_reason` と終端の `[DONE]` レコードを両方確認してから `done` を出します。途中で閉じたストリームから、不完全なツール呼び出しを実行へ渡してはいけません。

## まず動かす

テストは完全にオフラインです。

```bash
npm run test:s14
```

実モデルの総仕上げ課題では、ストリーミング Chat Completions と関数 / ツール呼び出しに対応する OpenAI 互換エンドポイントを設定します。

```bash
cp .env.example .env
# OPENAI_API_KEY と OPENAI_MODEL を設定します。
# OPENAI_BASE_URL の既定値は https://api.openai.com/v1 です。

npm run session:s14 -- "README.md を読み、このコースを三点で説明して"
```

このコマンドは Node の `--env-file-if-exists` フラグで `.env` を読み込みます。s13 の統合ランタイムを作り、`read_course_file` を公開し、最後にモデルの回答を表示します。このツールは、実行時の `cwd` ではなく `learn-pi-agent` モジュールの位置をルートとして固定します。さらにシンボリックリンクを解決し、コース内にある、隠しファイルではない通常ファイルのうち、50,000 バイト以下の有効な UTF-8 テキストだけを受け付けます。

それ以前のレッスン、`npm run test:s14`、`npm run check` に API キーは不要です。プロバイダーへのネットワークリクエストを送るのは `session:s14` だけです。

## コードの仕組み

### 1. 設定を明示する

`loadOpenAICompatibleConfig()` は `OPENAI_API_KEY` と `OPENAI_MODEL` を必須にし、`OPENAI_BASE_URL` は公式の `/v1` ベース URL を既定値にします。値がなければ `fetch` より前に失敗し、エラーは `.env.example` を案内します。

プロバイダーのファクトリーは、注入可能な `fetch` と `AbortSignal` も受け取ります。通常の実行では `globalThis.fetch`、テストではメモリ上の `Response` を使います。実モデルへのリクエストは、既定で 60 秒後にタイムアウトします。SDK も本番実行時の依存パッケージもありません。

### 2. ロールごとにメッセージを変換する

`createChatCompletionRequest()` は構造化された変換を行い、JSON 風の文字列置換には頼りません。内容を持つアシスタントブロックは、次の OpenAI 互換アシスタントメッセージになります。

```ts
{
  role: "assistant",
  content: null,
  tool_calls: [{
    id: "call_1",
    type: "function",
    function: { name: "read_course_file", arguments: "{\"path\":\"README.md\"}" },
  }],
}
```

対応する s04/s05 の `toolResult` は、同じ `tool_call_id` を持つ `tool` メッセージになります。この ID によって、モデルは根拠を自分が要求した操作に対応づけられます。ツールがある場合、リクエストには `parallel_tool_calls: false` を設定します。互換エンドポイントがこの設定を無視しても、アダプター側で 1 回の応答につきツール呼び出しを一つまでに制限します。

### 3. SSE パーサーでバイト境界を正しく扱う

`readSseData()` は一つのストリーミング `TextDecoder` を使い、読み取りの間に未完成のテキストバッファーを保持します。出力するのは完全な SSE レコードだけです。コメントや `data` 以外のフィールドはプロバイダーイベントにせず、同じレコード内に複数ある `data:` 行は SSE の規則に従って結合します。

テストでは、中国語を含む UTF-8 応答を 1、2、5 バイト単位で分割します。このテストに通ることで、伝送チャンクがコードポイントや JSON 文書を壊さないと確認できます。ストリーミングされた `refusal` も可視テキストへ変換し、空の成功結果として扱うことはありません。

### 4. `index` ごとにツール呼び出しを蓄積する

Chat Completions は、ストリーミングされるツール呼び出しを `index` で識別します。最初の差分が s03 のコンテンツブロックを作り、`toolcall_start` を出します。それ以降の差分は、`id`、`function.name`、`function.arguments` の断片を同じ蓄積器へ追加します。この総仕上げ課題が受け付けるのは、1 回の応答につき一つの呼び出しだけです。二つ目の `index` が現れた場合、どちらのツールも実行する前にプロトコルエラーにします。

`finish_reason: "tool_calls"` を受け取って初めて、`finalizeToolCall()` が引数文字列を解析し、JSON オブジェクトであることを確認します。その後、s02 のレジストリがハンドラーを呼ぶ前にスキーマを検証します。JSON の解析は「完全なオブジェクトか」を、レジストリの検証は「このツールの正しい入力か」を判断する、別々の境界です。

### 5. 失敗を見えるままにする

`OpenAIProviderError.kind` は次を区別します。

| 種別 | 例 | アダプターの動作 |
| --- | --- | --- |
| `authentication` | HTTP 401/403 | ステータスコードとプロバイダーのメッセージを含める |
| `rate_limit` | HTTP 429 | 一度報告し、再試行しない |
| `http` | その他の非 2xx 応答 | ステータスコードと長さを制限した詳細を含める |
| `network` | 接続またはボディー読み取りの失敗 | 元のメッセージを `cause` に残す |
| `aborted` | `AbortSignal` / `AbortError` | 中止を明示するエラーで止める |
| `protocol` | 不正な JSON、無効な差分、`finish_reason` / `[DONE]` の欠落 | 不完全なアシスタント応答を拒否する |

すべての失敗は、s03 が定義した終端の `ProviderEvent.error` に正規化されます。これにより s05 は `message_end` を閉じ、不完全なツール呼び出しは実行されません。実モデル用 CLI は同じエラーを観測し、Harness のライフサイクルが閉じた後に非ゼロの終了コードを返します。ライブラリ利用者は、例外専用の第二経路ではなく、一つの一貫したイベントストリームを受け取ります。

自動再試行は意図的に実装していません。本番用の再試行ポリシーには、冪等性、バックオフ、プロバイダーのヘッダー、キャンセル、可観測性への配慮が必要です。これらを最初のアダプターの中へ隠すと、誤った境界を学ぶことになります。

教育用アダプターは、リモート入力にも有限の上限を設けます。1 件の SSE イベントはデコード後 1,000,000 文字、SSE 応答全体は 4,000,000 バイト、HTTP エラーボディーは 64,000 バイトまでです。タイムアウトや上限超過は同じ終端エラーイベントになり、読み取り途中のリーダーはキャンセルされます。実モデルのループでは、モデル呼び出しを最大 4 回まで許可します。4 回目の応答でもツールを要求した場合、CLI は空文字列を成功結果として表示せず、上限到達を報告して非ゼロで終了します。これらは教材規模の安全策であり、本番環境の容量を推奨するものではありません。

## 実際のツールループ

実モデル用コマンドは、二つ目の Agent 実装を作りません。実プロバイダーと、読み取り範囲を制限したファイル用レジストリを、s13 の `createIntegratedHarnessRuntime()` へ渡します。

```text
ユーザーの質問
  -> 実モデルが read_course_file を要求
  -> s14 がツール呼び出しイベントを出す
  -> s05 がツールを検証して実行
  -> s13 がアシスタント応答 + toolResult を保存
  -> s14 が両方を二回目の API リクエストへ変換
  -> 実モデルがファイル内容に基づいて回答
```

これがコース最後の受け入れ確認です。使うのは実モデルですが、Harness は各レッスンで組み立ててきたものと同じです。

## 試してみる

1. `OPENAI_BASE_URL` を別の互換エンドポイントへ向け、ツール呼び出しに対応するモデルを選びます。同じ質問を実行し、失敗の原因が HTTP、SSE、メッセージ形式、ツール呼び出しの意味規則のどこにあるかを特定します。

2. `list_course_files` のような、読み取り範囲を制限した二つ目のツールを加えます。プロバイダーとループは変更しません。変更が必要なら、s02 の境界を見直します。

3. プロバイダーに `AbortController.signal` を渡し、最初の `text_delta` の後で中止します。その後に `done` やツール実行が発生しないことを確認します。

4. リクエストで並列呼び出しを無効にしているにもかかわらず、二つのツール呼び出しの `index` を含むフィクスチャを追加します。アダプターがプロトコルエラーを出し、どちらのハンドラーも実行されず、Harness がプロバイダーへ次のリクエストを送らないことを確認します。

最後に `npm run check` を実行します。検証はオフラインのままでなければいけません。

## メインラインへの接続

| 関心事 | 再利用する章 | s14 の責務 |
| --- | --- | --- |
| ツールの定義と検証 | s02 | モデルに見せるスキーマを直列化する |
| プロバイダーイベントの契約 | s03 | 正規化したテキスト / ツールイベントを出す |
| ツールの実行と結果 | s04/s05 | 結果を API メッセージへ戻す |
| ターンのコンテキスト | s06 | システムプロンプト、履歴、使用中のツールを直列化する |
| セッションとリソース | s07/s08 | 新しい動作は加えない |
| 拡張機能とポリシー | s09/s11 | 新しい動作は加えない |
| ランタイムと統合 | s10/s13 | 同じランタイムを作り、プロンプトを渡す |

s14 は末端のアダプターです。前の章から s14 をインポートすることはなく、既定のテスト経路にも認証情報は不要です。

## Pi ソースとの対応

対応関係は [pi-source.md](pi-source.md) にあります。Pi の OpenAI Chat Completions プロバイダーから始め、正規化されたイベントを `agent-loop.ts` まで追ってください。比較するのは行数ではなく責務です。実際の Pi は、多数のモデル系列、推論形式、使用量、費用、画像、互換性フラグを扱いますが、この教育用アダプターはそれらを対象外としています。

通信プロトコル上の動作は、公式の [Chat Completions API リファレンス](https://developers.openai.com/api/reference/resources/chat) と [function calling ガイド](https://developers.openai.com/api/docs/guides/function-calling) に従います。特に、ストリーミングされる `tool_calls[index]` の差分を蓄積し、JSON 引数を検証してから実行します。

## 意図的に省略するもの

- Responses API とプロバイダー固有の API
- 画像、音声、推論ブロック、マルチモーダルなツール結果
- トークン使用量、料金、コンテキストウィンドウの集計
- 並列再試行、代替モデル、バックオフ、再開
- 標準外のロールやフィールドに対するベンダー互換フラグ
- TLS / プロキシ設定と本番環境のシークレット管理
- ターミナルへのトークン単位の描画

これらは総仕上げ課題の対象範囲を定めるものであり、本番用プロバイダーが単純だという主張ではありません。

## まとめ

s03 は、ループが何を受け取るべきかを定義しました。s13 は、Harness のすべての仕組みをその契約の周囲に組み合わせられることを証明しました。s14 は、この抽象化の価値を最後に示します。ネットワークプロトコルをメモリ上のフィクスチャから実際の SSE へ変えても、ツールループを書き直す必要はありません。

オフラインでの再現性と実モデルを使った学習は対立しません。前者を土台に保ち、後者を明示的で検証可能な総仕上げ課題にします。
